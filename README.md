# agents-compared

A comparison of AI coding agents that refuses to rot.

**No model versions. No prices. No context-window sizes. No benchmark tables.** Those are
the four things every other comparison measures, and they are why every other comparison
is wrong within a month. What is left is what actually decides the choice and stays true:
the *shape* of each tool.

---

## The two questions that decide it

Search for "best AI coding agent" and you get a ranked list. The list is confident, it is
out of date, and it cannot be right for you, because whoever wrote it was not doing your
work.

Every tool here has the same shape:

1. It reads your project.
2. It proposes changes.
3. It applies them to real files.
4. You review what happened.

That shape is the thing worth learning — once you have it, switching tools costs an
afternoon rather than a month. So the comparison is not "which is best" but "which seat
do you want to sit in".

### 1. Where do you want to work?

| Shape | Where it lives | It suits you if |
|---|---|---|
| **Terminal** | a shell in your project folder | you want the agent next to git, tests, package managers and deploys |
| **Editor** | a panel inside your editor | you already live in an editor and want changes shown in place |
| **Remote** | someone else's machine | your work is well-specified up front and you review other people's code anyway |

This is ergonomics, not quality. It is also the single biggest factor in whether you are
still using the tool in a month.

### 2. How much control do you want per step?

Some setups show a plan and wait for approval before touching anything. Others go ahead
and let you read the diff afterwards. Neither is correct in general. If you are new, more
checkpoints teach you faster — you see the intent before you see the damage.

### What does not decide it

- **Benchmark scores** measure performance on standardised puzzles. Your codebase is not
  a standardised puzzle.
- **Which lab made it.** They leapfrog each other constantly.
- **What is trending.** The obvious winner of six months ago is a coin flip today.

## How to actually choose

Reading is not the answer. Take one real task from a project you have — a bug fix, a small
feature, a rename across a few files — and give it to two candidates with identical
context. Then compare three things:

1. Did it work?
2. Did you understand what it did?
3. How much did you have to correct it?

The second one is the sleeper. An agent that produces working code you cannot follow is
worse for you, today, than one that produces clumsier code you can read.

## Why this list stays alive

Comparisons die quietly: the vendor ships something, the page keeps saying the old thing,
and nobody notices for a year. A GitHub Action runs weekly, checks every outbound link,
watches each vendor's own feed, and opens an issue when a page looks contradicted by an
announcement. `news.md` is regenerated by the same job. Nothing here is updated by
remembering to update it.
